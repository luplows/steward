# steward v0.2.0

Steward can now land pull requests in the background, and move an installed project to a new
release. Where a project allows unattended landing, the coordinator lands each pull request that
has passed its review. `steward upgrade` opens a draft pull request moving a project's workflows to
another release. Steward still does not write code: people, or their own agent sessions, write the
pull requests.

## What you can do

- **Upgrade an installed project** with `steward upgrade --to vX.Y.Z`, which opens a draft pull request changing only steward's own workflows, and refuses when they aren't steward's.
- **Land unattended in the background.** Where `main`'s `steward.config.json` has `land: true`, the coordinator lands each pull request that has passed, on its scans.
- **Install with your checklist checked.** `init` warns, in its output and at the top of its pull request, when your `REVIEW.md` won't parse.
- **Install over your own workflows safely.** When a project already has workflows with steward's names that aren't steward's, `init` says so, installs nothing and exits 1.
- **Get every blocking finding in one review,** rather than one review at a time.
- **Run a rotation for another repository** with `steward rotation --repo <owner/name>`, from steward installed anywhere, against a checkout of that repository steward keeps.

## Get started

You need Node 24 (npm 11 or newer), git, the GitHub CLI, and the Claude Code or Codex CLI for the
reviewer. To install, in your project's checkout:

```sh
npx --yes --package=github:luplows/steward#v0.2.0 steward init
```

To move a project installed at v0.1.0:

```sh
npx --yes --package=github:luplows/steward#v0.2.0 steward upgrade --to v0.2.0
```

The [README](../README.md) has the full steps.

## Known issues

- **Workflows that run on `push` don't run after steward lands a pull request,** so CI or a deploy on `main` can fall behind. To run them, trigger on `workflow_run` of `Land approved PRs`, with the guard `github.event.workflow_run.head_sha != github.sha`. This works only on your default branch.
- **A landing doesn't close a linked issue,** whether unattended or by `steward land`. Close it by hand.
- **`init`'s files can fail a Prettier check.** Format them in the install pull request.
- **A pull request you merge by hand, such as `init`'s or `upgrade`'s, keeps its head branch on GitHub.** Only steward's own landings delete it. Delete it by hand.
- **Inspection raises an issue for the installation pull request,** since it is merged without a passing review, as `init` warns. Close it.

### For projects

- **`steward upgrade` is new.** Move a project from v0.1.0 with `steward upgrade --to v0.2.0`, run
  from steward at `v0.2.0`. Its pull request changes only the pin in each workflow `init` wrote.
- **The coordinator now lands.** Where `main` has `land: true`, a coordinator started from v0.2.0
  lands each pull request that has passed, where v0.1.0's only reviewed. Set `land: false` first
  if the project should not land unattended.
- The workflow files `init` writes, the example checklist and the settings keys are unchanged since
  v0.1.0, apart from the pin.
