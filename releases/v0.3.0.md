# steward v0.3.0

Steward can now write code, one approved unit at a time. A member of the crew approves a file or an
Issue with `steward handoff add`, and the coordinator codes it, pushes the branch and opens a linked
pull request, which is then reviewed and landed like any other. Nothing is coded without an
approval. Landing now closes the Issue a pull request completes, and upgrading explains what it
changes and why it refuses.

## What you can do

- **Have a unit coded.** Approve a file on `main` or an Issue with `steward handoff add`, and a coordinator started from v0.3.0 codes it to a `handoff/` branch and opens its pull request, with the unit linked and the approval's provenance in the body. `steward handoff list`, `show`, `reapprove` and `withdraw` manage approvals, and `steward coordinator status` shows the coding.
- **Prepare the coder's worktree your way.** The project's `setup` setting runs before each coder session, within its `timeoutMinutes`, in place of `npm ci`. A setup that fails or overruns stops the handoff before any model runs.
- **Keep your attribution rules.** Steward's own commits use the git identity of the project's checkout, and the coder reads your agent instructions for any attribution they require or forbid.
- **Close the Issue a pull request completes.** Where `unitLinks` includes `issue`, the runway closes it after landing, when the body has `Unit: #<n>` and `Closes #<n>` naming the same Issue.
- **Land unattended without waiting for another scan.** When the coordinator's own review passes a pull request, it waits for the gate's `review/agent` status to appear and lands it then, instead of on a later scan.
- **Install into a Prettier project.** The files `init` writes pass default Prettier, and `upgrade` accepts managed workflows Prettier has reformatted.
- **Review an upgrade before it lands.** `steward upgrade`'s pull request gives the evidence for what it changes, and each refusal says why, with steps to repair it safely.

## Get started

You need Node 24 (npm 11 or newer), git, the GitHub CLI, and the Claude Code or Codex CLI for the
reviewer and the coder. To install, in your project's checkout:

```sh
npx --yes --package=github:luplows/steward#v0.3.0 steward init
```

To move a project installed at v0.2.0:

```sh
npx --yes --package=github:luplows/steward#v0.3.0 steward upgrade --to v0.3.0
```

To have units coded, stop the coordinator on your machine, start it again from v0.3.0, and approve
a unit with `steward handoff add`. The [README](../README.md) has the full steps.

## Known issues

- **Workflows that run on `push` don't run after steward lands a pull request,** so CI or a deploy on `main` can fall behind. To run them, trigger on `workflow_run` of `Land approved PRs`, with the guard `github.event.workflow_run.head_sha != github.sha`. This works only on your default branch.
- **A bare `Unit: #<n>` closes no Issue.** Add `Closes #<n>` naming the same Issue.
- **An upgraded project's `steward.config.json` can fail a Prettier check,** since `upgrade` changes only the workflows. Format it in a pull request of your own.
- **The coder adds its tool's own attribution, such as `Co-Authored-By`, when your rules say nothing about it.** To keep it out, say so in your agent instructions.
- **Finished handoffs and failed reviews stay in `steward coordinator status`,** with no command to clear them.
- **The coder's environment has no GitHub API token, but is not isolated** from the machine's git credentials and other files.
- **GitHub warns that `actions/setup-node@v4` targets Node.js 20** in steward's workflow runs. The runs still pass.
- **An exclusion a pull request adds to its own unit counts only as an `**After review:**` line in that pull request's diff.** A case the unit's Out of scope already names needs no such line. If your CI refuses changes to a story in the pull request implementing it, add the case to the story's Out of scope in a separate pull request first.
- **Inspection raises an issue for the installation pull request,** since it is merged without a passing review, as `init` warns. Close it.

### For projects

- **Move to v0.3.0 with `steward upgrade --to v0.3.0`,** run from steward at `v0.3.0`. Its pull
  request changes only the workflows `init` wrote: the pin; `land-approved.yml`'s new
  `issues: write` permission, with which the runway closes a linked Issue; and double quotes in
  place of single in `land-approved.yml` and `inspection.yml`.
- **`steward handoff` is new,** and a coordinator started from v0.3.0 codes the handoffs approved
  with it, and nothing else. `upgrade` does not restart a coordinator: stop it and start it again
  from v0.3.0 by hand. Coding needs `user.name` and `user.email` set in the checkout of the project
  that steward keeps, and `unitLinks` on `main` including `file` or `issue`, for the kind of unit
  approved.
- **`setup` now runs before each coder session,** read from `steward.config.json` at the revision
  the coder's worktree is made from, within its `timeoutMinutes`. Set it to what the coder's worktree needs; `null` runs nothing. Nothing is
  run before a review.
- **To close an Issue on landing,** a pull request's body needs `Closes #<n>` as well as
  `Unit: #<n>`, with the workflows at v0.3.0.
- **`init` refuses a checklist path that does not end in `.md`.** An existing installation is not
  affected.
- The example checklist, the pull request template and the settings keys are unchanged since
  v0.2.0.
