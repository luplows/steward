# steward v0.1.0

The first release. Install steward in an existing project, and an AI reviewer checks each pull
request against your checklist and the issue or story file it links. Your issues and story files
stay as they are, and steward merges nothing unless you ask it to. Steward does not write code yet:
people, or their own agent sessions, still write the pull requests.

## What you can do

- **Install without risk to your files.** `init` opens a draft pull request for you to review, and overwrites nothing.
- **Require a passing review before merging,** with `steward protect`, where your GitHub plan offers branch protection.
- **Get reviews in the background.** `steward project activate` and `steward coordinator start` review open pull requests as they appear, across several projects, one at a time.
- **Merge a reviewed pull request** with `steward land <number>`, which refuses one that hasn't passed.
- **Spot what slipped through.** Inspection raises an issue for a merge with no passing review, and for a stalled pull request.

## Get started

You need Node 24 (npm 11 or newer), git, the GitHub CLI, and the Claude Code or Codex CLI for the
reviewer. In your project's checkout:

```sh
npx --yes --package=github:luplows/steward#v0.1.0 steward init
```

The [README](../README.md) has the full steps.

## Known issues

- **Workflows that run on `push` don't run after `steward land`,** so CI or a deploy on `main` can fall behind. To run them, trigger on `workflow_run` of `Land approved PRs`, with the guard `github.event.workflow_run.head_sha != github.sha`. This works only on your default branch.
- **`steward land` doesn't close a linked issue.** Close it by hand.
- **Your own checklist isn't checked at install.** A `## ` section with no numbered item gets every review refused, including the pull request that repairs it. Check your checklist before merging `init`'s pull request. If it happens later, remove `review/agent` from the required checks and merge the repair by hand.
- **`init`'s files can fail a Prettier check.** Format them in the install pull request.
- **`init` keeps files you already have,** so if your project has its own workflows with the same names, remove them first. When every file is there, `init` says the installation is complete, even if those files aren't its own.
- **Findings can arrive one review at a time.** Two reviews of the same commit can block on different things, and three blocks stop reviews of that pull request until you remove the `review-blocked` label.
